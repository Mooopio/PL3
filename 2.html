1. What is a type system?
Definition: a set of rules that assigns a type to constructs in a language: variables, expressions and functions.

Think of it as a rulebook that decides what may be combined with what. The slide shows the flow: Code → Type System Rules → Valid / Invalid.

Three jobs (all examinable)

  • Assigns types: maps constructs to types so operations depend on those types.
  • Prevents errors: catches invalid operations early; operations run only on compatible types.
  • Enables optimizations: the compiler can assume memory layout and operations, so it emits more efficient machine code (Code → Optimized Code).
Analogy: plugs and sockets. A type system refuses to let a UK plug into a US socket before anything catches fire.
2. Static vs dynamic typing
StaticDynamic
When checkedCompile timeRuntime
Errors foundEarly (compiler catches them)Late (during execution)
PerformanceFaster executionPotential overhead
SafetyStrong guaranteesFlexibility over safety
ExamplesRust, Java, C++Python, JavaScript, Ruby
int x = "hello";   // Java: ERROR at compile time
x = "hello"        # Python: fine
x = 5              # Python: still valid (x changes type)
Analogy: static = a spell-checker that blocks printing; dynamic = proofreading while reading aloud to an audience.
Trap: static/dynamic is about when checking happens. Strong/weak (next topic) is about coercion. They are independent axes.
3. Strong vs weak typing
StrongWeak
Implicit coercionNot allowedAllowed
ConversionsExplicit, requiredAutomatic
EffectPrevents accidental type errorsFlexible, but can cause bugs
ExamplesRust, Java, PythonJavaScript, PHP, C

The JavaScript example (memorise both lines)

"5" - 2   // 3     string "5" becomes number 5 (implicit)
"5" + 2   // "52"  number 2 becomes string "2" (implicit)

Same operand types, opposite coercion direction: - only makes sense for numbers, + also concatenates strings, so it picks strings.

Analogy: a strict translator refuses to guess and asks you to clarify; a lenient one silently guesses a meaning, sometimes wrongly.
Trap: Python is dynamic AND strong. Never say "dynamic means weak".
4. Polymorphism: parametric, ad-hoc, subtype

4a. Parametric

Functions or data structures written generically, operating uniformly on values regardless of their specific type. Type variables act as placeholders; the compiler instantiates the generic code with concrete types.
class Box<T> { T value; Box(T v){ value = v; } T getValue(){ return value; } }
Box<Integer> intBox = new Box<Integer>(123);   // T = Integer
Box<String> stringBox = new Box<String>("hello"); // T = String
intBox.getValue();    // 123
stringBox.getValue(); // hello

Benefits: code reuse across types, compile-time type safety, performance through inlining.

A labelled storage jar: the label (T) says what it holds, the jar design is the same.

4b. Ad-hoc

Functions/operators with the same name behave differently depending on argument types.
  • Compiler picks the implementation at compile time.
  • Distinguished by argument types, not return types.
  • Like overloading in Java/C++.
int add(int a, int b){ return a + b; }
double add(double a, double b){ return a + b; }
int result1 = calc.add(5, 10);       // int version
double result2 = calc.add(3.5, 2.1); // double version
The word “open” means something different for a door, a file and a bank account.

4c. Subtype

A value of a subtype can be used wherever a supertype is expected. Achieved through inheritance or interface implementation; methods can be overridden.
class Animal { void speak(){ System.out.println("Animal makes a sound"); } }
class Dog extends Animal { @Override void speak(){ System.out.println("Woof"); } }
class Cat extends Animal { @Override void speak(){ System.out.println("Meow"); } }
Animal a = new Dog();
a.speak();   // Woof (dynamic dispatch)

Benefits: reuse through inheritance, method overriding, dynamic dispatch by object type, flexibility.

Pitfall: the fragile base class problem: a change to a superclass can unintentionally affect all subclasses.
Any licensed driver can drive any vehicle in the “vehicle” class; each vehicle responds in its own way.
5. Type inference and Hindley-Milner
Type inference: in statically typed languages the compiler deduces types automatically, reducing explicit annotations.
Hindley-Milner (HM): foundational algorithm that infers the most general type of an expression, including polymorphic types. Used in ML and Haskell.
square x = x * x    -- inferred: Num a => a -> a

Process: (1) x has unknown type; (2) * adds a Num constraint; (3) the algorithm infers Num a => a -> a. Read it as: for any numeric type a, a function from a to a.

Benefits: concise, readable code; fewer repeated annotations; enables polymorphic functions and data structures; keeps static checking.

The slide also lists Python, Go, Rust and JavaScript under “other languages” with some form of inference.

A detective deducing the suspect’s type from clues (the operators used), without being told.
6. Dependent types
Types that depend on values. They blur the distinction between the type level and the term level. Examples: Idris, Coq.

This allows very precise specifications and compile-time verification of properties that would otherwise need runtime checks or formal proofs. Benefits: enhanced safety, precise specifications, elimination of certain classes of bugs. The slide diagram shows Type and Term depending on each other (Type(A)/Term(A), Type(B)/Term(B)).

Illustration (not on slide): a vector type that includes its length, so “head of an empty vector” does not compile.

A parking permit that names the exact vehicle. Types are no longer just categories, they carry facts.
7. Case study: Rust
  • Strong, static typing: checked rigorously at compile time, runtime errors prevented by construction, no implicit conversions.
  • Memory safety without a garbage collector: eliminates null pointer dereferences, prevents data races and use-after-free.
fn main() {
    let s1 = String::from("hello"); // s1 owns the data
    let s2 = s1;                    // ownership MOVED to s2
    println!("{}", s2);             // valid: "hello"
    // println!("{}", s1);          // COMPILE-TIME ERROR
}

Move semantics: assigning s1 to s2 transfers ownership; s1 is no longer valid. (The slide’s last key-points list is cut off, so rely on this example.)

Handing over the only house key. You cannot still use it after giving it away.
Trap: a move is not a copy, and the error appears at compile time, not at runtime.

Definitions

  • Type system: rules assigning types to variables, expressions, functions.
  • Static: checked at compile time. Dynamic: at runtime.
  • Strong: no implicit coercion. Weak: implicit coercion.
  • Parametric: generic, type variables. Ad-hoc: same name, behaviour by argument types. Subtype: subtype usable as supertype.
  • HM: infers most general type (ML, Haskell). Dependent types: types depend on values (Idris, Coq).

Rules and facts to recall instantly

  • "5" - 2 = 3 · "5" + 2 = "52"
  • square x = x * x gives Num a => a -> a
  • Overloading: argument types only, never return type; resolved at compile time.
  • Subtype polymorphism: dynamic dispatch; risk = fragile base class.
  • Rust: let s2 = s1; moves; using s1 afterwards = compile-time error. No GC.
  • Languages: Static: Rust, Java, C++ · Dynamic: Python, JS, Ruby · Strong: Rust, Java, Python · Weak: JS, PHP, C.
